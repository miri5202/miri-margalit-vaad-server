# שרת ועד בית 🏢

שרת למערכת ניהול הכספים של ועד הבית. ועד יכול לנהל כמה בניינים, ובכל בניין דיירים, תשלומים, הוצאות וחיובים חודשיים.
**טכנולוגיות:** Node.js, Express, PostgreSQL (עם הספרייה `pg`), התחברות עם JWT.

---

## 🚀 הפעלה ראשונה

1. **התקנה**
   ```bash
   npm install
   ```

2. **מסד נתונים - יש שתי אפשרויות:**
   - **בענן (מומלץ, חינמי):** פותחים חשבון ב־[Neon](https://neon.tech) ← יוצרים פרויקט ← מעתיקים את ה־Connection string. הכתובת נראית כך:
     `postgresql://user:password@ep-xxxx.neon.tech/neondb?sslmode=require`
   - **מקומי:** אם PostgreSQL מותקן על המחשב, יוצרים מסד בשם `vaad_bait` (למשל ב־pgAdmin).

3. **הגדרות:** יוצרים קובץ `.env` מתוך התבנית:
   ```bash
   copy .env.example .env
   ```
   וממלאים בו:
   - `DATABASE_URL`: כתובת החיבור מהשלב הקודם
   - `JWT_SECRET`: מחרוזת ארוכה ואקראית כלשהי

   > ב־Notepad הקובץ עלול להישמר בטעות כ־`.env.txt`. עדיף לערוך ב־VS Code.

4. **יצירת הטבלאות** (מוחק טבלאות קיימות!)
   ```bash
   npm run db:init
   ```

5. **נתוני דוגמה** (מוחק את כל הנתונים הקיימים!)
   ```bash
   npm run seed
   ```
   נוצרים 3 בניינים ומשתמשים לבדיקה. הסיסמה של כולם `123456`, ואפשר להתחבר **עם אימייל או עם טלפון**:
   | תפקיד | אימייל | טלפון | בניין |
   |---|---|---|---|
   | ועד | `admin@vaad.test` | `0500000001` | מנהל את "הזית 8" ואת "הרימון 3" |
   | ועד | `admin2@vaad.test` | – | מנהל את "האלון 15" |
   | דיירים | `apt1@vaad.test`, `apt2@...`, `apt4@...`, `apt5@...` | `0501111111` וכו' | הזית 8 |
   | דייר בלי אימייל | – | `0503333333` | הזית 8, דירה 3 |
   | דייר ביחידת דיור | – | `0503333300` | הזית 8, יחידה **3א** (₪80 לחודש) |
   | דיירים | `rimon1@vaad.test`, `rimon2@vaad.test` | – | הרימון 3 |
   | דייר | `alon1@vaad.test` | – | האלון 15 |

   **קודי הצטרפות לבניינים:** הזית 8 = `ZAYIT8`, הרימון 3 = `RIMON3`, האלון 15 = `ALON15`

6. **הפעלה**
   ```bash
   npm run dev
   ```
   בדיקה: לפתוח בדפדפן `http://localhost:5000/api/health`. אמור להופיע `{"ok":true,"db":"connected"}`.

## 🗄️ הטבלאות

**users** - משתמשים
`id`, `full_name`, `email` (ייחודי, לא חובה), `password` (מוצפנת), `role` (`admin`/`resident`), `building_id`, `apartment`, `phone` (ייחודי, לא חובה)
- **חובה אימייל או טלפון** (לפחות אחד), כי איתם מתחברים.
- `is_unit` (`isUnit` ב-API): `true` = הדייר גר ביחידת הדיור של הדירה (למשל "3א").
- טלפון נשמר בספרות בלבד: `050-123 4567` ו-`+972501234567` נשמרים שניהם כ-`0501234567`.
- ועד (`admin`): בלי בניין ובלי דירה. הבניינים שלו מסומנים ב־`buildings.manager_id`.
- דייר (`resident`): חובה בניין ודירה.

**buildings** - בניינים

| שדה ב־API | עמודה בטבלה | הערות |
|---|---|---|
| `name` | `name` | שם לתצוגה, למשל "הזית 8" |
| `address`, `city` | `address`, `city` | כתובת ועיר |
| `apartmentsCount` | `apartments_count` | מספר הדירות (1–500). דירות ממוספרות 1 עד המספר הזה |
| `monthlyFee` | `monthly_fee` | דמי ועד חודשיים לדירה |
| `dueDay` | `due_day` | עד איזה יום בחודש משלמים (1–28). אחריו חיוב שלא שולם הופך ל"באיחור" |
| `unitFee` | `unit_fee` | דמי ועד ליחידת דיור (סכום אחד לכל היחידות בבניין) |
| `unitApartments` | `unit_apartments` | לאילו דירות יש יחידת דיור, למשל `[3, 5]` ← יחידות "3א" ו-"5א". אפשר לשלוח גם טקסט `"3, 5"` |
| `joinCode` | `join_code` | קוד הצטרפות לדיירים (6 תווים). **חוזר רק לוועד** |
| `managerId` | `manager_id` | הוועד שמנהל את הבניין |

> מחיקת בניין מוחקת גם את הדיירים והתנועות שלו (`ON DELETE CASCADE`).

**transactions** - תנועות כספיות (האובייקט המרכזי)

| שדה ב־API | עמודה בטבלה | ערכים / הערות |
|---|---|---|
| `id` | `id` | מספר, נוצר אוטומטית |
| `buildingId` | `building_id` | הבניין שהתנועה שייכת לו |
| `type` | `type` | `income` (הכנסה) / `expense` (הוצאה) |
| `amount` | `amount` | מספר חיובי. נשמר כ־`NUMERIC(10,2)`, מדויק לכסף |
| `date` | `date` | `YYYY-MM-DD` |
| `category` | `category` | `monthly_fee` `cleaning` `elevator` `electricity` `repairs` `gardening` `other` |
| `apartment` | `apartment` | חובה בהכנסה: הדירה ששילמה |
| `isUnit` | `is_unit` | `true` = התשלום של יחידת הדיור של הדירה (למשל "3א"). בהוצאה תמיד `false` |
| `supplier` | `supplier` | חובה בהוצאה: שם הספק |
| `paymentMethod` | `payment_method` | `cash` `transfer` `check` `credit` |
| `status` | `status` | `paid` (שולם) / `pending` (ממתין) / `late` (באיחור) |
| `description` | `description` | טקסט חופשי, עד 500 תווים |
| `createdBy` | `created_by` | מי הוסיף (קשור לטבלת users) |

> בטבלה השמות כתובים ב־`snake_case`, כמקובל ב־SQL. ב־JSON שחוזר ללקוח הם ב־`camelCase`, כמקובל ב־JavaScript. ההמרה נעשית בשאילתות עם `AS`.
>
> את התרגום לעברית (`cleaning` ← "ניקיון") עושים בצד הלקוח.

## 🔐 התחברות - איך זה עובד

1. הלקוח שולח אימייל וסיסמה ל־`POST /api/auth/login`.
2. השרת בודק את הסיסמה מול הגרסה המוצפנת ששמורה במסד (bcrypt).
3. אם הסיסמה נכונה, השרת מחזיר **טוקן** (JWT) ואת פרטי המשתמש.
4. הלקוח שומר את הטוקן ושולח אותו בכל בקשה בכותרת:
   ```
   Authorization: Bearer <הטוקן>
   ```
5. ה־middleware `requireAuth` בודק את הטוקן ומזהה את המשתמש.
   `requireAdmin` בודק שהתפקיד הוא `admin`.

## 🛣️ נתיבי ה־API

כל הנתיבים מתחילים ב־`/api`. 🔒 = צריך להיות מחובר. 👑 = ועד בלבד.
כל מה ששייך לבניין נמצא תחת `/buildings/:buildingId/...`. לפני כל נתיב כזה ה־middleware `loadBuilding` בודק שלמשתמש מותר לגשת לבניין: ועד רק לבניינים שהוא מנהל, ודייר רק לבניין שלו. אחרת חוזר 404.

### התחברות
| שיטה | נתיב | מה עושה |
|---|---|---|
| POST | `/auth/register` | הרשמת ועד חדש: `{ fullName, email?, phone?, password }` (חובה אימייל או טלפון) ← `{ token, user }` |
| POST | `/auth/join` | הצטרפות דייר עם קוד הבניין: `{ joinCode, apartment, fullName, phone, password, email? }` ← `{ token, user }` |
| POST | `/auth/login` | גוף: `{ login, password }`. `login` = אימייל **או** טלפון (גם `email` עדיין עובד) ← `{ token, user }` |
| GET 🔒 | `/auth/me` | מחזיר את המשתמש המחובר (לבדיקה בטעינת האפליקציה) |
| GET | `/options` | רשימות הערכים לשדות הבחירה (לטפסים ולסינון) |

`user` = `{ id, fullName, email, role, buildingId, apartment, phone }`. לדייר `buildingId` הוא הבניין שלו, ולוועד הוא `null`.
**שתי דרכים להכניס דיירים:**
1. **קוד הצטרפות**: הוועד מעביר לשכנים את קוד הבניין (למשל בקבוצת הוואטסאפ), וכל שכן נרשם בעצמו עם הקוד, מספר הדירה, טלפון וסיסמה שהוא בוחר.
2. **הוספה ידנית**: הוועד מוסיף דייר עם טלפון או אימייל (לפחות אחד), וקובע לו סיסמה ראשונית.

### בניינים
| שיטה | נתיב | מה עושה |
|---|---|---|
| GET 🔒 | `/buildings` | ועד: הבניינים שלו. דייר: הבניין שלו. כולל `residentsCount`, `balance`, `totalDebt` |
| POST 👑 | `/buildings` | הוספה: `{ name, address, city, apartmentsCount, monthlyFee?, dueDay? }` |

| POST 👑 | `/buildings/:buildingId/join-code` | יצירת קוד הצטרפות חדש (הישן מפסיק לעבוד) ← `{ joinCode }` |

## 🏠 יחידות דיור
- בבניין מגדירים **`unitFee`** (דמי ועד ליחידה) ו-**`unitApartments`** (לאילו דירות יש יחידה).
- דייר ותשלום מסומנים עם **`apartment` + `isUnit`**: `{ apartment: 3, isUnit: true }` = יחידה **3א**.
- **חיובים חודשיים**: כל דירה מחויבת בדמי הוועד של הבניין, וכל יחידה ב-`unitFee` (אם הוא גדול מ-0).
- **מי שילם / חייבים**: היחידות מופיעות כשורות נפרדות (`isUnit: true`), מיד אחרי הדירה שלהן.
- **"התשלומים שלי"**: דייר ביחידה רואה רק את התשלומים של היחידה, ודייר בדירה רק של הדירה.
- אי אפשר להוריד יחידה מהבניין אם יש בה דייר או תשלום.

**איך עובדים החיובים:**
- כל חיוב נשמר כתנועת הכנסה בקטגוריה `monthly_fee`, בתאריך הראשון לחודש, בסטטוס `pending`.
- דירה שכבר יש לה דמי ועד באותו חודש מדלגים עליה. לכן לחיצה כפולה לא יוצרת כפילויות (`skipped`).
- אחרי `dueDay` בחודש, חיוב שעדיין ממתין הופך אוטומטית ל־`late`. הבדיקה נעשית בכל כניסה לבניין (`services/fees.js`), כך שאין צורך בתזמון.
- כשדייר משלם: `PATCH /transactions/:id/pay`. התאריך לא משתנה, כדי שהתשלום יישאר משויך לחודש שלו בטבלת "מי שילם".
- **תשלום חלקי:** אם הדייר שילם רק חלק, שולחים את הסכום: `PATCH /transactions/:id/pay` עם `{ "amount": 100 }`.
  החיוב מתפצל לשניים: 100 ₪ מסומנים "שולם", ונוצר חיוב חדש של 50 ₪ עם הסטטוס הקודם (ממתין / באיחור), אותו תאריך, והתיאור "(יתרה)".
  התשובה היא התשלום ששולם, ובתוכו `remainder` - חיוב היתרה. בטבלת "מי שילם" החודש מופיע כ-`partial` עד שהיתרה משולמת.
  סכום גדול מהחיוב, או תשלום חלקי על חיוב ששולם כבר - מחזירים שגיאה 400.

### לוח הודעות - `/buildings/:buildingId/announcements`
| שיטה | נתיב | מה עושה |
|---|---|---|
| GET 🔒 | `/` | כל ההודעות של הבניין: נעוצות קודם, ואז מהחדשה לישנה. כל הודעה: `{ id, title, body, pinned, authorName, createdAt, updatedAt }` |
| POST 👑 | `/` | פרסום: `{ title, body, pinned? }` (כותרת עד 120 תווים, תוכן עד 2000) |
| PUT 👑 | `/:id` | עריכה. אפשר לשלוח רק את מה שהשתנה, למשל `{ pinned: true }` |
| DELETE 👑 | `/:id` | מחיקה |

## ⚠️ פורמט שגיאות

כל שגיאה חוזרת באותו מבנה, וזה נוח לטיפול בטפסים:
```json
{
  "message": "יש שדות לא תקינים",
  "errors": { "amount": "הסכום חייב להיות מספר חיובי" }
}
```

| קוד | מתי |
|---|---|
| 400 | נתונים לא תקינים |
| 401 | לא מחובר / הטוקן פג |
| 403 | אין הרשאה (למשל דייר שמנסה להוסיף תנועה) |
| 404 | לא נמצא |
| 409 | ערך כפול (למשל אימייל שכבר קיים) |

## ☁️ העלאה לענן (Render)

1. מעלים את הקוד ל־GitHub (בלי `node_modules` ובלי `.env` - כבר מוגדר ב־`.gitignore`).
2. מסד הנתונים: Neon (כמו בשלב 2 למעלה), או ב־Render: **New ← PostgreSQL**, ומעתיקים את ה־External Database URL.
3. ב־Render: **New ← Web Service** ← בוחרים את המאגר.
4. Build Command: `npm install` · Start Command: `npm start`
5. ב־Environment מוסיפים את המשתנים מקובץ `.env`, ומעדכנים את `CLIENT_URL` לכתובת של צד הלקוח אחרי שיעלה.
6. פעם אחת בלבד, מהמחשב, עם `DATABASE_URL` של מסד הענן בקובץ `.env`, מריצים `npm run db:init` ו־`npm run seed`.

## 🗣️ מה צריך לדעת להסביר (לפי הדרישות)

- **לאיזה API ה־React פונה:** לנתיבים שבטבלאות למעלה. אחרי התחברות: ועד מקבל את רשימת הבניינים מ־`GET /buildings` ובוחר בניין, ודייר עובר ישר לבניין שלו לפי `user.buildingId`.
- **מה נשלח לשרת:** טוקן בכותרת `Authorization`, ובהוספה ועריכה את שדות התנועה בגוף הבקשה (JSON).
- **מה חוזר:** אובייקט JSON. ברשימות `{ items, total, page, pages }`, ובשגיאה `{ message, errors }`.
- **איך נשמר המידע:** בטבלאות PostgreSQL שמוגדרות ב־`db/schema.sql`. השרת בודק את הנתונים ב־`validators.js`, ובנוסף הטבלה עצמה אוכפת כללים עם `CHECK` (למשל סכום חיובי, והכנסה חייבת מספר דירה).
- **הגנה מ־SQL Injection:** הערכים לא נכתבים ישירות בשאילתה, אלא נשלחים בנפרד כפרמטרים (`$1`, `$2`...).
- **איך עובדות ההתחברות וההרשאות:** סיסמה מוצפנת ב־bcrypt ← בהתחברות מקבלים JWT ← כל בקשה עוברת ב־`requireAuth`, ונתיבי ועד עוברים גם ב־`requireAdmin`. בנתיבים של בניין, `loadBuilding` בודק שהבניין שייך למשתמש. כל שאילתה כוללת `building_id`, כך שאי אפשר להגיע לנתונים של בניין אחר. דייר רואה רק את התשלומים של הדירה שלו ואת ההוצאות של הבניין שלו.
